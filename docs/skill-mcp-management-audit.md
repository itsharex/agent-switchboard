## 2. 阻断与高优先级发现

### F01 / P1：命令与 Store 重复获取不可重入锁

证据：`src-tauri/src/commands/extensions.rs:335` 持有 `save_lock()`，随后在第 369 行调用 `save_definition()`；后者在 `src-tauri/src/extensions/store.rs:184` 再次获取同一 Mutex。`next_generation()` 在第 132 行也独立获取此锁。应用计划的提交闭包在命令文件第 1975 行取得锁，第 1984 行又调用带锁的 `save_binding()`。

影响：新建 MCP 的保存会阻塞；应用计划可能在已经写入客户端文件后阻塞，无法正常提交或释放目标锁。

验证：以实际 Store 实现复现同线程持锁后调用 `next_generation()`，700ms 内无法完成；源码锁顺序确认这是自锁，不是一次普通慢操作。

修复：让扩展库的一次批量提交拥有锁；通过持锁事务对象执行内部写入，删除命令层手工持锁再调用公开带锁方法的路径。不要换成可重入锁来保留重叠职责。把批量提交和 generation 更新作为一个持久化提交单元设计，不能只修死锁而保留半提交。

### F02 / P1：同一目标的后续步骤失败时，前面已经落盘的步骤没有回滚

证据：`crates/asb-switch/src/extensions/transaction.rs:527` 将成功步骤暂存于目标内的 `step_results`，第 578 行才整体转入全局 `completed`。此前任何步骤失败直接返回，回滚集合中没有本目标已经完成的写入。文档替换后、写后校验返回错误的窗口也需要纳入撤销记录。

验证：一个目标包含两份 TOML 写入；第一份从 `value = 1` 写成 `value = 2`，第二份因无效 TOML 失败。执行器返回失败，但第一份仍为 `value = 2`。

修复：以每一个可见文件变更为事务步骤，提前准备可恢复的撤销信息，完成一次变更便进入回滚集合；错误路径不能因尚未构造 `CompletedStep` 而失去已发生的副作用。测试需覆盖同目标、跨目标、替换后的验证失败和日志失败。

### F03 / P1：执行器产生的日志无法被恢复器正确读取，且恢复没有与执行互斥

证据：`transaction.rs:376` 写入首条 Prepared JSON 时不带换行；第 942 行的 `append_journal()` 在其后直接拼接下一条 JSON，随后以整文件替换方式“追加”。`recovery.rs:174` 按行解析，第一行包含两个 JSON 对象会解析失败。现有恢复测试使用手工构造的日志，没有验证实际执行器日志。

验证：真实执行器在注入库提交失败后留下的 `journal.jsonl`，第 1 行不是合法 JSON。

另外，`src-tauri/src/commands/extensions.rs:274` 在列表读取过程中直接执行恢复；恢复路径没有获取与写入相同的目标锁并判断活动事务。日志格式修复后，这会暴露刷新列表与活动写入相互干扰的风险。`StepStarted` 的信息也不足以恢复“已替换、尚未记 StepCompleted”的文档窗口。

修复：统一日志写入/解析契约；记录顺序、换行、持久化屏障和提交判定；在可见替换前持久化恢复所需的目标前状态、备份位置及预期后摘要。读取列表保持只读。恢复取得相同锁并确认事务不活动后执行；未解决的恢复状态由后端阻断涉及同一目标的新写入。不得静默吞掉提交日志错误再宣告完成。

### F04 / P1：客户端文件与扩展库没有形成统一的失败/崩溃恢复边界

证据：命令文件第 1975—2029 行依次写绑定、基线、删除记录、更新 generation。任一中间步骤失败，外层执行器仅能撤销客户端写入；已写入的库记录缺少相同操作的撤销或提交判定。

影响：修掉死锁后，仍可能出现文件回到了旧状态、绑定却已更新，或部分绑定被删除的情况。

修复：沿用当前本地文件存储，先在事务区准备该操作完整的库变更与撤销信息，再由同一个执行器协议完成客户端和库的持久化提交。多文件无法单次原子替换，需要明确可恢复的提交点，不能将逐个原子写文件等同于批量原子事务。读者必须读到同一 generation 的完整状态。无需为此另引入数据库或第二套执行器。

### F05 / P1：计划有效期、定义版本和凭据版本没有在应用时核对

证据：命令文件第 803—804 行将 `created_at` 和 `expires_at` 都设置为当前时间；第 1869 行创建空 `secret_versions`。第 1958 行起应用计划仅从内存移除计划后调用执行器，未核对有效期、当前定义 revision、库 generation、凭据版本。现有文件摘要检查不能替代这些条件。

验证：有效期结束于 2000 年的计划仍被执行器成功应用。结合命令层检查可确认生产调用链也没有补上有效期判断。

修复：在唯一计划契约中保存生成时的必要版本快照，创建正确 TTL；持锁后、任何写入前重验所有前置条件。失效返回重新预览，不能静默用新定义或新密钥改写旧预览。同步更新计划生产者、执行消费者、DTO 和测试，删除恒空/无消费字段以及重复的待提交绑定来源。

### F06 / P1：Codex 项目 MCP 使用了 Claude 的路径与语法，能力校验没有成为硬约束

证据：命令文件第 1015 行的 `ProjectShared` 分支不区分客户端，第 1018 行固定调用 `claude_project_mcp_path()`，第 1021 行固定 JSON；后续 Codex 渲染为 TOML。`ProjectPrivate` 也采用 Claude 路径。`crates/asb-core/src/extensions/validate.rs:370` 的作用域支持判断未接入生产绑定校验链。

影响：Codex 项目安装计划目标错误并会遇到语法校验失败；只在界面展示“能力”并不能阻止直接命令调用。宿主专用 Skill 的跨端绑定也需要在同一后端校验处约束。

修复：一个带类型的目标解析函数拥有“客户端 × 资源 × 作用域 → 路径、语法、能力条件”。所有安装、启停、撤下和恢复共用它。不支持的组合直接返回结构化错误，不能回退到另一客户端路径。能力未知或实测未通过时在计划生成和应用边界拒绝相应写入。

### F07 / P1：停用提交旧绑定，启用撤销规则未充分证明所有权

证据：命令文件第 1297 行设置 `next.desired = Disabled`，预览也使用 `next`，但第 1311 行提交集合压入原始 `binding`。Skill 启用的 `clear_disable_steps()` 第 1356 行起主要按规则值判断是否删除；项目 Claude 的停用与清除规则还存在作用域不一致。

影响：客户端已停用而库仍为 Enabled；再次启用可能无法撤销正确位置的规则，或移除原本属于用户的禁用规则。用一个新文档基线替换目录基线也会丢失目录所有权信息。

修复：提交状态直接来自已验证计划，删除独立重复的绑定列表。基线能够同时表达目录内容与该绑定拥有的启停规则，并保存规则原值和位置。启用只撤销本应用这次写入所拥有的改变；外部禁止仍应显示有效状态受限。

### F08 / P1：历史“恢复”不是可靠的指定操作撤销

证据：命令文件第 88 行 `ARCHIVED_BASELINES` 是进程内存；第 2151 行恢复读取此缓存。第 2165 行起优先读取当前绑定基线，随后使用 `original_value`，而不是所选操作的前状态。Skill 基线第 1180 行 `backup_reference` 为 None，恢复第 2236 行缺少引用就跳过。第 2285 行恢复计划没有提交相应绑定状态。

影响：卸载后重启丢失恢复资料；恢复一次更新可能回到首次安装前；Skill 历史记录存在但无可恢复目录；文件恢复后库状态未同步。

修复：每次操作持久化该操作的前后状态及备份摘要/清单，绑定基线与操作快照职责分开。所选历史恢复生成正常事务计划，包含文件和库变更，并验证当前后状态没有被外部替换。删除 `ARCHIVED_BASELINES` 以及从“当前基线”猜测历史的路径。

### F09 / P1：编辑 MCP 会删除同一服务内的宿主未知字段

证据：`crates/asb-core/src/extensions/mcp.rs:483` 整个替换 `mcp_servers.<key>` 的表，而非仅更新声明拥有的字段。保留其他服务及顶层键，并不等于保留当前服务内未知字段。

验证：输入服务含 `host_option = true`，编辑其受管字段后该键消失。

修复：适配器按受管键补丁合并；移除字段、切换传输、删除整个自有服务分别有明确语义。JSON 对应路径、Skill 规则也执行相同的未知字段保留契约。已有同名原生项和重复绑定在计划生成时报告冲突，只有明确接管才能建立所有权；不要直接覆盖后把当前内容当作新基线。

### F10 / P1：MCP 检测无法保证有界完成

证据：`src-tauri/src/extensions/checks.rs:397` 在终止子进程之前 `reader.join()`；标准长期运行的 MCP 服务不关闭 stdout，读取线程持续等待，外层清理无法执行。第 140、207 行把环境变量引用传成字面量 `${NAME}`，直接进程/HTTP 请求不会替它展开。读行和 HTTP `.text()` 的体积限制也没有覆盖读取本身。

修复：实现一个可取消且有总截止时间的检测生命周期；先结束传输和子进程树、关闭管道，再有限等待工作线程。环境变量在检测边界按名称解析，仅在内存使用。对单条消息、累计体积、分页和总时长同时设限。版本支持必须与设计所引用的官方协议/SDK能力核实，未支持版本明确失败。删除被替代的自写协议路径，不能同时保留两套探测器作兜底。

本项为代码路径审查，未在真实第三方服务上执行命令或发送请求。

### F11 / P2：Skill 内容存储不能无损往返

证据：`src-tauri/src/extensions/store.rs:58` 的 `StoredFile` 无类型字段，第 481 行以 `size == 0` 判断目录。保存同一 digest 目录直接逐文件写入，并未保证发布后的版本不可变。`commands/extensions.rs:1880` 的 staging 写入未恢复文件权限；多处目录遍历/摘要构造需要统一模式位语义。

验证：保存一个普通空文件再读取，实际得到 Dir。

修复：在唯一内容清单中显式保存 File/Dir、规范化 mode、大小与摘要；所有扫描、来源解压、库保存、部署和恢复复用同一规范。版本先写临时目录并验证，按内容地址一次发布；已存在版本只校验，不原位覆盖。平台不支持的 mode 语义需在摘要规则中明确，不能靠空文件或操作系统偶然行为推断。

### F12 / P2：界面已有按钮，但若干操作没有对应完整流程

证据：`src/pages/ExtensionsPage.tsx:38` 的新增入口仅有 newMcp/discover。第 194 行保存始终传空 expectedRevision；第 226 行原生 MCP“导入”只预填名称/传输，其他参数丢失，并把非 stdio 一律当 HTTP。`src/app/useExtensions.ts:179` 的更新仅调用 `updateSkillDefinition()`，未继续生成部署更新计划。

剩余需要补齐：

- GitHub/本地来源选择、来源候选预览、固定 ref/commit、完整目录查看与来源持久化。
- 区分“加入库”和“接管已有安装”，原生 MCP 导入保留参数和原键；JSON/TOML 片段导入有类型校验。
- MCP 编辑与 revision 冲突反馈；显示名和 native key 独立，显式改键更新引用。
- Skill 更新比较上次部署、当前目录和新来源，处理本地改动，再选择绑定生成更新计划；不能只改库后提示更新完成。
- 自建 Skill、本地副本编辑和版本生成；依赖 MCP 配置与用户选择后的组合计划。
- 原生 OAuth 授权引导、能力与有效状态解释、项目及同名来源影响说明。
- 设计承诺的批量选择、固定版本及可移植导出/导入，应逐条验收；只有类型或命令不算已交付。

发现阶段也需要保留读取失败、损坏文档等诊断，不能通过 `unwrap_or_default()` 将失败显示为空库。列表 DTO 当前直接携带定义，需核查 URL、参数及 Plain 值的展示边界；由后端投影安全展示数据，使用假敏感标记测试脱敏，不能依赖页面各自遮挡。

## 4. 无兼容、无过渡的补全顺序

这里的“无兼容”指不留下旧内部数据形状、双读双写、回退实现和临时桥接；不表示取消 Codex/Claude 原生行为差异或破坏用户已有配置。“无技术债”以无已知阻断项、无失效路径、验收证据完整为目标，不能承诺未来绝无缺陷。

### 修复批次一：收敛契约与事务基础

处理 F01—F05、F11，先于扩展更多写入入口。

1. `asb-core::extensions` 拥有完整的当前计划、内容清单、操作快照与基线契约。一个计划直接携带执行后应提交的状态，消除 `PendingPlan` 与 `PlannedTarget` 重复但可能分歧的绑定来源。
2. Store 提供受锁约束的批量提交边界；`asb-switch::extensions` 仍是唯一真实文件执行入口，掌管每步撤销、日志和库提交。Tauri 命令负责组织依赖和错误映射，不再内嵌另一套事务规则。
3. 修正内容类型和不可变版本发布，然后统一摘要规则及权限语义，防止后续恢复建立在错误摘要上。
4. 同步所有直接生产者、消费者、序列化校验、DTO、fixture；移除旧字段、恒空字段和失效帮助函数。先做必需的职责归位，不为拆分而增加通用框架。

验收：六个反例变绿；真实命令保存和应用在截止时间内返回；每个目标的每个 I/O 失败点都满足“恢复完整旧状态，或进入可解释且阻断冲突写入的恢复状态”；客户端和库不得静默分裂。

### 修复批次二：闭合所有权、作用域与历史语义

处理 F06—F09。

1. 将所有操作收敛到同一个目标解析、能力检查和字段级适配器。
2. 安装、接管、更新、启用、停用、撤下各有明确前置状态和可验证后状态；保留未受管字段和外部规则。
3. 历史恢复只依赖持久化操作快照，移除内存归档与从当前基线推断历史的实现。

验收：客户端 × 资源 × 有效作用域覆盖；不支持组合在写前失败；安装→停用→启用→更新→撤下→进程重启→恢复完整通过；已有规则、同名冲突、本地修改、部分撤下和库引用均有反例测试。

### 修复批次三：完成发现、导入、来源与检测

处理 F10、F12 的后端能力及数据展示边界。

1. 发现返回候选与诊断，不进行修复写入；损坏和无权限与不存在分开处理。
2. 原生导入从解析结果产生完整草稿，未知传输明确不可导入，不伪装为 HTTP。
3. 来源解析、不可变版本、三方更新复用批次一的内容契约。
4. 检测只保留一套经过版本核实的实现，使用本地模拟服务覆盖常驻进程、空响应、畸形消息、输出超限、分页、超时与取消。不调用业务工具。

验收：读取操作零真实配置写入；导入往返保持语义；检测在总截止时间内完成或取消，无遗留子进程；假敏感值不进入列表、预览、日志与错误。

### 修复批次四：接通用户流程并按事实更新文档

补齐 F12 的前端入口及操作结果，页面仅消费后端已判定的能力、冲突与状态。

1. 从设计的每一条用户操作反查到页面入口、命令、领域服务、执行器、持久化后状态和验证用例，缺一项就标注未完成。
2. 增加少量命令边界集成测试，避免所有页面交互仅依赖 mock；组件测试保留输入、错误与无障碍等自身职责。
3. 执行当前支持平台的文件/目录故障测试和真实客户端隔离加载测试。未验证能力必须真正被后端门禁拒绝，不能只附“未核实”文案。
4. 最后更新 `progress.md` 的阶段结论、README 产品能力、DESIGN 交互事实和设计文档的实现状态；删除与实际不符的完成声明。

验收：每个声称支持的操作都有完整执行和重启后状态证据；不存在只改库却宣称部署成功、只展示按钮却无工作流程、读取失败却展示空状态的路径。

## 5. 删除清单与最终复核

必须随修复删除：命令层重复 Store 锁；计划之外的重复提交状态；内存历史归档；失效期/凭据版本占位；整服务覆盖补丁；跨客户端路径回退；非 stdio 一律转 HTTP；以 size 推断目录；整文件重写冒充追加日志；列表自动恢复；被替代的协议探测器。删除同时搜索生产调用、测试 fixture、前端契约和文档，避免留下无人消费的类型或旧入口。

旧内部 schema 不以“缺字段默认补齐”或同时识别两种形状维持运行。当前若仅为开发样本，使用隔离路径重建测试状态；若已存在用户扩展数据，先清点并保全，不擅自删除或覆盖。确需转换时应另行定义一次性的离线转换边界并验证业务含义，正式运行时只接收唯一当前形状。

最终完成条件：本报告的高优先级问题均有修复与回归证据；设计承诺的流程有端到端对应关系；没有第二套内部契约或写入入口；故障恢复能跨进程重启；未核实能力不能写入；状态文档与实际证据一致。仅全量测试原样通过、类型检查通过或成功打包，都不能替代这些条件。
